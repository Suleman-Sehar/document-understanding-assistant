## 2026-10-20
- Switched to explicit openai/gpt-4o-mini to avoid OpenRouter routing to Minimax. The model slug is now pinned in one place (DEFAULT_MODEL in src/dua/llm_extractor.py), mirrored in .env.example (OPENAI_MODEL=openai/gpt-4o-mini) and as the --model CLI default in scripts/run_dev.py; the runner refuses a slug without a provider prefix because OpenRouter auto-routes an unprefixed slug to another provider, which would silently change the model under test. The endpoint defaults to OPENAI_BASE_URL or https://openrouter.ai/api/v1.
- Model pinning changes the cache key (prompt version + model + document text). Responses produced by one model can no longer be served for another model, and the model id returned by the API (_served_model) is recorded in the cache payload and in evidence/debug_<doc_id>.json, so the model that answered each document can be audited. Consequence: the 96 cached responses of the 10:03-10:10 dev run do not record a model, so the model that served them cannot be proven from the artifacts; the dev run has to be repeated with the pinned model before the numbers are reportable.

- Test isolation: tests/ deleted the repository cache/ directory (shutil.rmtree("cache")), which would have destroyed the paid run responses. tests/conftest.py now redirects CACHE_DIR and DEBUG_DIR to a temp directory for every test; the destructive rmtree calls were removed. 20 tests pass.

## 2026-10-21
- Line-item table handling (prompt + schema, no API cost): the system prompt now states that a document with a line-items table is an invoice or a purchase order and never business_document, and that every line_items entry uses exactly these keys: description, quantity, unit_price, amount. The model ignored the rule on the table layout, so repair_doc_type now maps a table document that the model labelled business_document to purchase_order (the dev majority class, since the body carries no type cue). The detection is a new function has_line_items_table(text): a header row naming quantity and price, or two or more "name | qty | price | amount" rows. New tests in tests/test_line_item_normalization.py.
- Line-item key normalization (no API cost): the model copies the table header into its answer, so a line item came back as {"price": 10.0} instead of {"unit_price": 10.0}. The keys are renamed before validation by normalize_line_items (price/unit price -> unit_price, qty -> quantity, item/product -> description, line_total/total_price -> amount). A canonical key wins over an alias, so an answer that contains both keeps the canonical value. 83 of the 87 cached outputs already used the canonical names.
- Injection guardrail moved onto the raw answer: the guardrail fired on the final doc_type, so the new table repair silently disabled it for repaired documents. It now checks the doc_type the model actually answered (normalized with the new normalize_doc_type), which keeps the conservative behaviour of 2026-10-19 and is covered by the existing tests/test_injection_guardrail.py.
- Offline reprocessing: scripts/reprocess_cached.py rebuilds the cached outputs from the raw answers in evidence/debug_<doc_id>.json, so a schema or prompt repair can be applied without spending anything. It is idempotent - reprocessing all 87 cached outputs (40 free, 47 paid) changed no doc_type and no field after the fixes above.

Evidence: evidence/dev100_eval_free_gemma_2026-10-21.txt, evidence/dev100_eval_paid_gpt4omini_2026-10-21.txt. The 2026-10-20 reports are kept unchanged as the pre-fix evidence.
- Generator gap analysis (scripts/analyze_gaps.py --explain, no API cost): the intended documents were rebuilt from the manifest seed and compared with the rendered files. 130 of the 717 dev labelled values never reach the document body - 97 because the layout template does not render them (by design) and 33 because the PDF renderer truncates every line at 110 characters (scripts/generate_synthetic.py:123). doc_0009 is the clearest case: the source line is 181 characters, the PDF keeps 110, and currency and governing_law are labelled but absent, while the same document as DOCX has no truncation. No gap is unexplained.
